# 审核系统闭环修复设计

## 1. 目标与范围

本次在保留现有审核状态机、修订模型、规则集版本和清理 worker 的前提下，收口前后端审核生命周期。目标是让当前公开内容、待审内容、审计历史和规则集状态各自只有一个事实来源。

本次包含：

- 碎语图片从私有暂存、审核、正式发布到私有审计的完整生命周期。
- 审核队列与审计历史分离，并在管理端查看正文、图片和操作事件。
- 修正规则导入、模板、候选发布和规则启停状态。
- 修正 Web 图片遮罩判断、管理端修订行标识和刷新时序。
- 消除 worker 空轮询产生的 `record not found` 错误日志。
- 将非当前审计数据和图片保留期统一为 90 天。

生产环境尚未启用审核，因此不迁移现有审核内容、图片对象或历史修订。数据库结构变更仍通过正常 migration 发布。

## 2. 核心原则

1. 审核队列只表达当前状态，历史版本不参与队列投影。
2. 每张图片由后端返回明确展示模式，前端不根据内容整体状态推断遮罩。
3. `/moderation` 只保存私有暂存或审计对象，公开图片只使用正式业务路径。
4. 规则启停以当前已发布 ruleset 为准，未发布候选不得改变线上投影。
5. Garage 与 MySQL 没有分布式事务，所有跨资源写入必须具备补偿和提交后清理。

## 3. 审核队列与审计历史

### 3.1 当前队列

`GET /admin/moderation/items` 每个 `moderation_item` 最多返回一条当前修订：优先 `pending_revision_id`，否则返回最新已决修订。状态筛选作用于该当前修订，不再直接联表返回全部历史版本。

桌面和移动端行标识统一使用 `item_id:revision_id`。审核成功后刷新方法必须等待新请求完成，再关闭详情弹窗。

### 3.2 审计历史

新增管理员分页接口：

`GET /admin/moderation/items/{id}/history?page=1&page_size=20`

响应包含：

- 修订版本、提交正文、发布正文、风险、策略和审核状态。
- 修订图片快照及 `visible / pending / blocked` 展示模式。
- 提交、重新提交、通过、修正通过、驳回、隐藏和恢复等操作事件。
- 操作人、理由、创建时间和审核时间。

管理端审核详情增加“当前内容 / 审计历史”页签。`superseded` 仅在历史中展示，中文文案为“已被新版本替代”。历史接口仅允许管理员访问，分页上限 100。

## 4. 碎语图片生命周期

### 4.1 对象路径

- 待审暂存：`moderation/staging/moments/{userID}/{uploadID}/{hash}.{ext}`。
- 当前公开：`moments/{userID}/{momentID}/{hash}.{ext}`。
- 私有审计：`moderation/history/moments/{itemID}/{hash}.{ext}`。

服务端生成全部对象 key。客户端提交的旧 URL 必须验证对象存在、属于当前用户及允许的前缀。

### 4.2 首次通过

1. 提交阶段只写 staging 对象和修订图片快照。
2. 人工通过、修正通过或自动通过时，将本次图片复制到正式路径。
3. MySQL 事务更新通过状态、修订图片引用、`moment_media` 和 materialized revision。
4. 事务失败时删除本次新复制的正式对象；事务成功后删除不再引用的 staging 对象。

### 4.3 后续编辑

- 新修订继续使用独立 staging 对象，不影响当前公开图片。
- 审核通过时，保留图片不搬运；新增图片复制到正式路径。
- 被新版本删除的旧公开图片先复制到私有审计路径，事务中将相关历史修订引用改为审计 key；提交后删除旧公开对象。
- 驳回或被新修订替代的 staging 图片保留至审计期限，不能继续出现在公开 `moment_media` 中。

对象复制、数据库更新和对象删除均要求幂等。共享对象删除前必须按 object key 检查修订和当前媒体引用。

### 4.4 管理端图片检查

当前详情和审计历史均返回可访问的管理端图片 URL。私有图片通过受管理员鉴权保护的读取路径或短期签名 URL 提供，不把对象存储原始私有地址直接交给浏览器。

## 5. 规则管理与导入

### 5.1 multipart 上传

`POST /admin/moderation/rule-imports` 使用 multipart：

- admin 身份与现有临时上传限流。
- 仅允许 UTF-8 CSV/TXT，使用现有配置限制单文件大小和最大行数。
- handler 只绑定表单和文件；service 负责真实内容、默认值和资源边界校验。
- 对象上传成功但任务创建失败时删除对象；任务创建成功后由 worker 接管生命周期。

错误报告下载必须返回实际 CSV 内容；报告不存在或任务状态不允许时返回明确业务错误。

### 5.2 导入字段和校验

CSV 字段为：

`name,rule_type,pattern,category,effect,risk_level,priority`

- `rule_type` 支持 `keyword / regexp / composite`，为空时默认 `keyword`。
- 正则使用 Go RE2 编译校验。
- 组合规则至少包含两个有效 `&&` 信号。
- `allow` 仅允许关键词。
- 校验名称、模式长度、枚举、优先级、文件内重复和当前规则集重复。
- 任一错误使整批进入 `invalid`，不创建可发布候选，并生成逐行错误报告。

TXT 继续表示“一行一个关键词”，其余字段使用上传表单默认值。

模板只包含说明和标准表头；关键词、正则和组合示例放在表头前的注释说明中，不放会被直接导入的有效数据行。

### 5.3 规则状态和候选版本

规则 `active` 按当前已发布 ruleset 计算：

`activated_ruleset_id <= current && (deactivated_ruleset_id IS NULL || deactivated_ruleset_id > current)`

默认“全部”查询也必须计算真实状态。候选版本的未来启停值在发布前不能改变当前列表或分类器。初始种子只保留一条启用的安全基线规则，不再创建“停用规则示例”。

## 6. 前端展示语义

- API 为每张图片返回展示模式和管理端检查 URL。
- Web 碎语卡片、详情弹窗和编辑回显只根据单图展示模式选择原图、遮罩或阻断占位。
- 正常公开图片不会因为内容存在待审修订而被整体遮罩；作者仍可看到其待审图片提示。
- 管理端规则导入发送真实文件，展示校验、候选构建、待发布、失败和错误报告状态。
- 管理端规则列表直接使用后端 `active`，不自行推断规则集版本。

前端当前存在未提交的碎语列表和弹窗改动。实施时必须保留并先核对这些差异；发生重叠时以当前用户改动为基础合并，禁止覆盖。

## 7. worker、日志与清理

- 导入队列和候选构建队列为空属于正常 idle，不使用会产生 `gorm.ErrRecordNotFound` 错误日志的查询方式。
- 空轮询不输出错误；状态恢复、任务失败和真实数据库错误继续使用结构化 zap 日志。
- 不通过全局忽略所有 `record not found` 来掩盖真实业务问题。
- 非当前修订、操作日志、staging 和私有审计图片统一保留 90 天。
- 当前 materialized、approved、pending 修订及其对象不受过期清理影响。
- 清理顺序为数据库引用判定、删除对象、删除无引用记录；单批失败可在下一轮幂等重试。

## 8. API Risk Pass

1. 谁能调用：队列、历史、规则和私有图片检查均为 admin；普通用户只能提交和读取自己的待审投影。
2. 输入边界：分页最大 100；碎语最多 9 图；规则上传沿用文件大小、行数、模式长度和规则数量配置。
3. 资源成本：上传、图片处理、对象复制和规则构建沿用用户/admin 限流及单 worker 串行构建。
4. 失败收口：对象成功而 DB 失败执行补偿；DB 成功后再删除旧对象；所有删除可重试。
5. 旧状态清理：更新图片列表时只清理不再公开且已转存审计的对象；规则候选失败不影响当前发布版本。

## 9. 测试与验收

### 后端

- repository：当前队列投影、历史分页、规则 active 计算、空轮询和清理引用使用 `go-sqlmock`。
- service：三种通过路径、保留/新增/删除图片、对象补偿、90 天清理和三类规则导入使用 gomock/fake store。
- handler：历史接口权限与分页、multipart 成功/超限/格式错误、错误报告下载使用 `httptest`。
- 修改接口后运行 `make swag` 并确认 DTO 未暴露 `model.*`。

### 前端

- API：multipart、历史 DTO 和文件下载。
- Admin：当前队列唯一行、真实刷新、历史页签、图片检查和三类规则导入。
- Web：公开原图、作者待审图、普通访客遮罩及多次编辑替换图片。

### 完成条件

- 后端 `go test ./...` 通过。
- 前端 API、Web、Admin 相关测试、类型检查和构建通过。
- 空闲 worker 不再持续打印 `record not found`。
- 通过图片只从正式路径公开；旧图不出现在当前媒体列表，并能在 90 天内从审计历史查看。
- 默认规则列表正确显示真实启停状态，CSV 可导入三类规则。

## 10. 实施顺序

1. 修正队列投影并增加审计历史读模型和接口。
2. 建立图片正式化、审计转存和补偿编排。
3. 修正规则 active 投影、multipart 导入、解析器和模板。
4. 调整 worker 空轮询和 90 天清理。
5. 接入 Admin/Web 前端并统一图片展示模式。
6. 运行全量验证、Swagger 生成和针对性回归测试。
