# 审核后互动通知与审核队列邮件设计

## 1. 背景与目标

启用内容审核后，评论和回复改走统一的 `moderation.Submit` 路径。该路径不会执行评论服务原有的 `comment_created`、`reply_created` 和 `guestbook_created` 事件发布逻辑；人工审核事务当前只生成一条发给内容作者的 `system_notice`。

因此现状存在两个缺口：

- 评论或回复自动通过、人工通过后，文章作者、碎语作者、留言板博主或被回复人收不到互动通知。
- 系统没有把尚未报告给博主的待审队列聚合为运营邮件。

本次目标：

1. 互动内容只在首次公开后通知真正的互动接收人。
2. 自动通过立即产生互动事件，人工审核内容在通过后产生互动事件。
3. 待审内容可靠进入专用邮件 Outbox，经短聚合窗口和全局最短发送间隔后只发给一名博主。
4. 复用现有 SMTP 构造注入、结构化日志和 worker 租约原则，不引入外部 MQ。

本次不包含前端审核页面改造，也不改变点赞仅发送站内通知的现有策略。

## 2. 已确认的产品语义

### 2.1 互动通知

| 内容类型 | 首次公开后的接收人 | 事件类型 | 可进入邮件队列 |
| --- | --- | --- | --- |
| 文章一级评论 | 文章作者 | `comment_created` | 是 |
| 碎语一级评论 | 碎语作者 | `comment_created` | 是 |
| 留言板留言 | 留言板所属博主 | `guestbook_created` | 是 |
| 文章评论回复 | 被回复人 | `reply_created` | 是 |
| 碎语评论回复 | 被回复人 | `reply_created` | 是 |
| 留言回复 | 被回复人 | `reply_created` | 是 |

约束：

- 自动通过：内容成功公开后创建互动事件。
- 人工通过、修正后通过：审核事务成功并公开内容后创建互动事件。
- 驳回、待审、被新版本替代：不创建互动事件。
- 已经公开内容的编辑通过不再次发送“评论/回复了你”。
- 自己评论自己的内容或自己回复自己，沿用 dispatcher 的 actor/recipient 去重规则，不通知自己。
- 审核结果 `system_notice` 继续只发送给内容作者，与互动接收人通知相互独立。

### 2.2 回复邮件时机

邮件必须以“内容已经公开”为前提：

- 自动通过的回复，在自动通过事务完成后进入现有通知邮件链路。
- 需要人工审核的回复，只在人工通过或修正后通过后进入邮件链路。
- 审核前和审核失败后均不向被回复人发邮件。

互动事件进入现有 dispatcher、planner、sender 后异步发送。当前循环分别约为 5 秒、30 秒和配置的 12 秒；这是最终一致的后台处理，不承诺固定秒级送达。

## 3. 互动事件架构

### 3.1 原子性

审核状态转换、业务内容公开投影和待分发互动事件必须在同一 MySQL 事务中持久化。不能在 handler 中补发，也不能依赖请求返回后的 goroutine，否则进程退出或事件写入失败会造成永久漏通知。

审核应用层负责决定“本次转换是否为首次公开”和构造领域通知意图；repository 只把意图转换为 `notification_event` 行，不承担接收人策略判断。

一次人工决策允许原子追加多条通知意图：

- 给内容作者的审核结果 `system_notice`。
- 首次公开时给互动接收人的 `comment_created`、`reply_created` 或 `guestbook_created`。

### 3.2 首次公开判定

只有转换前不存在已通过版本、转换后产生首个公开版本时，才创建互动事件。该判断基于审核项的 approved/materialized 状态，不使用修订版本号猜测。

这样可正确区分：

- 新评论首次自动通过：发送。
- 新评论首次人工通过：发送。
- 首次内容被管理员修正后通过：发送。
- 已公开评论编辑后再次通过：不发送。
- 同一审核命令幂等重放：不重复写事件。

### 3.3 通知上下文

互动事件保留现有通知展示需要的稳定快照：来源正文、根对象标题或摘要、被引用内容、父评论 ID和显式接收人。接收人和快照由只读上下文解析器加载，通过接口注入审核 service。

新建对象的业务 ID 在审核事务内分配。通知意图使用“当前审核主体”引用，repository 在同一事务中用实际分配的主体 ID 填充 `source_id`，并依赖唯一幂等键避免重放产生重复事件。

## 4. 审核队列邮件方案

### 4.1 选择专用 Outbox

审核队列邮件不复用普通互动通知事件。它表达的是“当前仍待审且尚未报告的工作项”，必须在发送前过滤已经处理的修订，还要维护独立的聚合窗口和最短间隔。

使用专用 Outbox 可以避免：

- 普通通知事件已经落库，但发送时内容早已审核完成。
- 仅靠扫描时间戳无法判断某个修订是否已经报告。
- SMTP 失败后错误启动冷却或永久丢失任务。

### 4.2 持久模型

新增两个内部模型，不直接暴露给 HTTP API 或 Swagger：

`moderation_review_email_task`：每个进入 `pending` 的审核修订一条任务。

- `revision_id` 唯一，保证审核提交或幂等重放不会重复建任务。
- 保存 `item_id`、状态、`available_at`、`batch_id`、错误与时间戳。
- 状态使用 `pending / batched / sent / skipped`。

`moderation_review_email_batch`：一封稳定的审核摘要邮件。

- 保存接收人用户 ID、邮箱快照、状态、任务数和稳定 Message-ID。
- 保存 `scheduled_at / sent_at`、租约、尝试次数、下次重试时间和最近错误。
- 状态使用 `pending / sending / sent`；失败回到 `pending` 并退避。

planner 创建 batch 并把 task 绑定到 batch 的操作必须处于同一事务。存在未完成 batch 时不再规划新 batch，避免 sender 尚未成功时并行越过冷却限制。

### 4.3 任务产生

审核策略将某个新修订置为 `pending` 时，在同一事务创建 email task。自动通过、高风险直接阻断、驳回和仅观察模式不创建任务。

若待审修订在规划邮件前已经通过、驳回、被替代或删除，planner 将 task 标记为 `skipped`，不写入邮件批次。

## 5. 配置与接收人

配置放在 `moderation.review_email`：

```yaml
moderation:
  review_email:
    enabled: true
    recipient_user_id: 1
    aggregation_window_seconds: 60
    min_interval_seconds: 1800
    poll_interval_seconds: 15
```

默认值：

- `enabled=true`，但只有审核总开关开启且邮件基础设施可用时启动。
- `recipient_user_id=1`。
- 首封聚合窗口 60 秒。
- 成功邮件之间最短间隔 1800 秒。
- worker 轮询间隔 15 秒。

接收人只允许一名用户。发送前必须确认配置用户存在、具有 admin 角色且主邮箱已经验证。未显式配置用户时使用 ID 1；显式配置的用户无效时记录结构化错误并重试，不能静默改发给 ID 1 或其他管理员。

这是博主运营告警，不读取普通互动通知偏好；是否启用由 `moderation.review_email.enabled` 单独控制。邮箱地址在创建 batch 时做快照，保证重试目标稳定。

## 6. 聚合与冷却算法

设最早一条未报告且仍待审任务创建时间为 `T`，上一封成功发送时间为 `S`：

```text
next_send_at = max(T + aggregation_window, S + min_interval)
```

没有上一封成功邮件时，只使用 `T + aggregation_window`。

具体行为：

1. 队列长期为空，第一条任务到达后等待约 1 分钟收集同批内容。
2. 邮件成功后，30 分钟内的新任务继续积累，不立即发送。
3. 若新任务在冷却结束前不足 1 分钟到达，仍须满足它自己的 1 分钟聚合窗口。
4. 发送前重新锁定并检查修订状态，只包含仍为当前待审版本的任务。
5. 已经成功报告过但仍未审核的旧任务不重复提醒；后续新待审修订进入下一封。
6. 邮件为空时不创建 batch，也不更新上一封成功时间。

轮询造成的实际发送误差最多约一个 `poll_interval`，默认约 15 秒。

## 7. 邮件内容

主题建议为：`待审核内容提醒（N 条）`。

正文包含：

- 当前邮件包含的新增待审总数。
- 各内容的类型、作者、提交时间和安全截断后的纯文本摘要。
- 指向管理端审核队列的站点绝对链接。
- 若正文条目达到固定展示上限，显示“其余 N 条请进入后台查看”，但 batch 仍记录本次包含的完整任务集合。

邮件不得包含命中规则详情、内部处罚分数、私有图片对象 key 或未经清洗的 HTML。

## 8. worker 与失败处理

新增审核邮件 worker，由 bootstrap 构造注入 repository、用户/角色目录、Mailer、配置和 zap logger。禁止使用全局 db、mailer 或 logger。

处理顺序：

1. planner 清理失效任务并在到期时创建稳定 batch。
2. sender 通过数据库租约领取 batch，渲染当前 batch 快照并发送。
3. SMTP 成功后，在事务中将 batch 和所属 task 标记为 `sent`。
4. SMTP 失败或数据库暂时错误时释放租约、记录错误并退避重试同一个 batch。

只有 SMTP 成功并成功提交状态后才启动 30 分钟冷却。失败不把任务标记为已报告。SMTP 属于外部副作用，无法提供严格 exactly-once；稳定 Message-ID、稳定 batch 和租约用于尽量降低超时重试产生的重复邮件。

接收人配置错误、用户不再是 admin 或邮箱未验证时，不创建新 batch；保留任务并按较长退避重试，同时输出不含邮箱明文的结构化告警。

## 9. 测试设计

### 9.1 审核后互动通知

- 六类内容分别覆盖自动通过、人工通过和修正后通过。
- 首次公开创建正确事件、接收人、actor、source/root 和快照。
- 驳回、待审、编辑通过和幂等重放不创建重复互动事件。
- 同一人工审核事务同时落作者审核结果和互动事件。
- 事务任一写入失败时审核状态、公开投影和事件整体回滚。
- dispatcher 验证互动事件继续按现有偏好和邮箱条件创建邮件任务。

### 9.2 审核队列邮件

- task 与待审修订原子创建，`revision_id` 唯一。
- 首任务等待 60 秒；同窗口任务合并。
- 成功邮件后 1800 秒冷却；边界时间使用可注入时钟验证。
- 发送前通过、驳回、替代或删除的任务标记 `skipped`。
- 已报告但未处理的旧任务不重复发送。
- SMTP 失败不推进冷却，重试保持相同 batch 和 Message-ID。
- worker 租约过期后可恢复；并发 worker 不重复领取同一 batch。
- 默认用户 1、配置用户、非 admin、未验证邮箱和缺失用户分别测试。

repository 使用 `go-sqlmock`，service/worker 使用 gomock 或轻量 fake，时间必须通过构造注入，不能依赖真实 sleep。

## 10. 验收条件与风险

完成条件：

- 审核开启时，六类互动在首次公开后均产生正确站内通知；符合现有邮件条件时进入邮件队列。
- 需要人工审核的回复在审核前不通知被回复人，审核通过后才通知。
- 第一批待审内容约 1 分钟后形成一封邮件，后续成功邮件间隔不少于 30 分钟。
- 已处理内容不会出现在尚未规划的审核摘要中，同一修订不会被成功报告两次。
- 相关分层测试和 `go test ./...` 通过。

主要风险：

- SMTP 成功但状态提交前进程退出仍可能产生重复邮件，系统只能做到 at-least-once 和幂等保护。
- 审核事务新增两类 Outbox 写入后，必须控制索引和查询批次，避免待审高峰扩大锁范围。
- 互动事件修复必须以“首次公开”而非“审核通过”作为触发条件，否则编辑审核会骚扰接收人。
