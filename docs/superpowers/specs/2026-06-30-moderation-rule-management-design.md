# 审核规则管理与大规模词库设计

## 1. 目标与范围

为现有内容审核系统补齐后端规则管理 API、批量导入流水线和管理端页面。系统面向单机单实例部署，日常预计维护约 10 万条有效关键词，容量上限按 50 万条设计。

本期实现：

- 管理员查询、筛选、新增、修改、启用和停用规则。
- 批量启用或停用规则，单次最多 1000 条。
- 按分类、风险、类型、来源和状态管理规则。
- 使用当前或候选规则集执行文本试跑。
- CSV 与 UTF-8 TXT 全链路流式导入、预检、错误报告、确认发布和任务历史。
- CSV/TXT 导入模板下载与当前规则流式导出。
- 基于紧凑 Aho–Corasick 索引的大规模关键词匹配。
- 规则集版本追溯、候选构建、内存阈值保护和单实例热切换。
- 管理端桌面表格、移动端卡片、导入进度和候选版本试跑。

本期不实现：

- 内置或自动下载第三方敏感词库。
- 多实例版本广播、Redis 同步或实例就绪协调。
- 多人审批、草稿协作和规则集回滚。
- AI 语义审核、谐音模型、图片识别或外部付费审核服务。
- 导入时覆盖现有规则；导入只增加新规则，重复项必须先处理。

公开词库的授权、准确性和时效性由管理员确认。规则数量不等于合规能力，关键词层只负责明确的文本信号，语境不确定内容继续进入人工审核。

## 2. 关键约束

- 生产数据层继续使用 MySQL，运行时匹配在 Go 进程内完成。
- 普通审核请求不得逐条查询规则或线性遍历全部关键词。
- 规则内容不可原地覆盖；修改生成新规则 ID，历史审核记录仍能读取旧内容。
- 每条审核版本继续保存实际使用的 `ruleset_version` 和 `rule_match_ids`。
- 任意导入行失败时整批不可发布；当前规则集不得出现部分生效。未发布候选中断行不向规则列表展示，并由幂等清理删除。
- 新索引构建期间旧索引继续服务；候选失败不得影响当前规则集。
- 单次内容最多持久化 128 个确定性排序后的命中规则 ID；风险计算不截断，并显式保存是否发生截断。
- 所有管理接口仅注册在现有管理员路由组，响应使用 `dto.*`，不得返回 `model.*`。
- 日志只记录任务、版本、规则 ID、统计和错误类型，不记录完整敏感词内容。

## 3. 方案选择

采用“MySQL 规则事实源 + 单实例 Go 内存索引”。MySQL 保存规则、版本、候选停用和导入任务；后台构建候选索引文件；发布事务提交后在当前进程内原子替换不可变快照，分类路径不增加读锁。

不采用独立审核服务，因为当前只有一个博客后端实例，独立服务会增加网络超时、熔断和部署成本。不采用数据库实时匹配，因为 10 万至 50 万规则下无法满足审核写请求的延迟和稳定性要求。

## 4. 规则语义

### 4.1 规则类型

- `keyword`：普通关键词，进入 Aho–Corasick 索引。
- `regexp`：Go RE2 正则，数量受独立上限约束。
- `composite`：由至少两个 `&&` 信号组成，沿用现有组合规则语义。

关键词、正则和组合规则均保存：可选名称、分类、风险等级、优先级、来源引用和规则效果。批量规则不生成无意义名称。

### 4.2 风险与效果

- 风险等级保持 `low`、`medium`、`high`。
- 规则效果分为 `review` 和 `allow`。
- `review` 规则参与风险计算，所有命中取最高风险。
- `allow` 仅支持关键词，用于抑制其覆盖范围内的 `review` 关键词命中，不能绕过正则、组合规则或独立于该范围的其他命中。
- 高风险规则只应承载高置信信号；语境不明确规则使用中风险并进入人工审核。

### 4.3 分类与来源

首期分类使用受控值：`politics`、`pornography`、`violence`、`terrorism`、`gambling`、`drugs`、`fraud`、`abuse`、`advertising`、`minors`、`other`。DTO 同时返回稳定键和中文显示名，前端不自行翻译后端未知值。

来源在 `moderation_rule_source` 中去重保存，规则只引用 `source_id`。每次导入只能选择一个来源；需要区分来源时拆成多个导入任务。来源用于区分手工维护、采购词库或特定数据批次，不用于授权判断。

### 4.4 归一化与重复

关键词使用与分类器相同的 Unicode、繁简、全半角、大小写、零宽字符和异常分隔符归一化。原模式和归一化结果都不得超过配置长度。活动规则的重复键由 `effect + rule_type + normalized_pattern` 计算 SHA-256。数据库只保存原模式和摘要；构建时重新归一化，摘要碰撞时重新归一化原模式并比较，不能只凭摘要认定重复。

- 文件内部出现相同重复键：对应行报错。
- 与当前活动规则重复：返回已有规则 ID 并报错。
- 任意重复都使整批导入不可发布。
- 正则和组合规则按规范化前的精确模式计算重复键，避免改变表达式语义。

## 5. 数据模型与历史追溯

### 5.1 `moderation_rule`

在现有表上迁移为以下事实字段：

- `id`
- 可空 `name`
- `rule_type`、`pattern`、`dedupe_hash`
- `category`、`effect`、`risk_level`、`priority`
- `source_id`
- `activated_ruleset_id`、可空 `deactivated_ruleset_id`
- 可空 `replaces_rule_id`
- 创建、更新时间

删除现有 `enabled` 和 `ruleset_version`，不新增 `normalized_pattern`、`root_rule_id` 或 `created_by`。名称、类型、模式、分类、效果、风险、优先级和来源创建后不修改；只有已发布的停用操作可以填写 `deactivated_ruleset_id`。

修改规则时创建新 ID，并用 `replaces_rule_id` 指向旧记录。停用填写旧记录的停用规则集；重新启用时创建内容相同的新记录。规则属于已发布版本 `V` 的条件为：其启用规则集已经发布且 ID 不大于 `V`，并且停用规则集为空或 ID 大于 `V`。

失败候选的规则行通过启用规则集状态排除，不会在后续版本中意外生效。失败或取消候选按保留期删除。历史审核项保存的规则 ID 永远指向当时实际命中的不可变规则内容。

### 5.2 `moderation_rule_source`

来源表保存唯一名称和时间字段。规则只保存 `source_id`；来源仅在没有规则或导入任务引用时允许清理。固定分类继续使用短字符串，避免为少量闭合枚举增加运行时联表。

### 5.3 `moderation_ruleset`

自增主键 ID 直接作为规则集版本，不再保存第二个 `version` 字段。每个候选或已发布版本保存：

- `status`：`building`、`ready`、`publishing`、`published`、`failed`、`superseded`
- `base_ruleset_id`
- 总规则数和各类型数量
- 索引常驻字节、构建峰值估算、构建耗时
- 索引对象键、二进制格式版本和 SHA-256 校验和
- 操作者、失败类型和时间字段

详细节点、边和输出统计作为构建诊断信息返回，不参与正确性判断。任一时刻只有一个 `published` 版本作为当前事实源；旧版本在同一事务中转为 `superseded`。失败版本允许造成 ID 空洞，ID 不复用。

### 5.4 候选停用

`moderation_ruleset_removal` 只保存候选规则集需要停用的规则 ID。新增规则已经作为未发布事实写入 `moderation_rule`，不再复制到通用变更表。发布成功后停用关系已经物化到规则行，该候选的 removal 行可以清理。

### 5.5 导入任务

`moderation_rule_import` 保存文件名、格式、大小、对象键、`source_id`、默认字段、校验状态、行数统计、错误报告对象键、候选规则集 ID、操作者和时间字段。

导入表只维护 `queued`、`validating`、`valid`、`invalid`、`canceled` 校验状态；构建、待发布、发布和失败状态统一读取关联的 `moderation_ruleset`，避免两张表维护同一事实。不创建 `moderation_rule_import_item`。原始文件和错误报告默认保留 7 天，任务摘要默认保留 30 天。

### 5.6 审核命中截断

现有 `moderation_revision` 和 `moderation_attempt` 增加 `rule_matches_truncated`。`rule_match_ids` 最多保存配置数量；该布尔值表示还有命中未写入 JSON。`risk_level` 始终基于全部匹配状态计算，不因 ID 枚举预算或持久化上限降低。

## 6. 运行时匹配索引

### 6.1 紧凑 Aho–Corasick

关键词使用按 rune 构建、以连续数组保存的单棵 Aho–Corasick 自动机，allow 与 review 共享前缀节点。节点、边、失败指针、suffix link 和直接输出区使用扁平切片，不为每个节点分配 `map[rune]`，也不把失败链输出复制到子节点，避免前缀嵌套词库造成平方级输出膨胀。

运行时规则元数据使用平行数值数组，只保留规则 ID、风险、优先级、效果和模式长度。名称、分类、来源和原模式不进入运行时快照。规则序号用 `uint32`，数据库 ID 单独保存在 `[]uint64` 中。

一次分类流程：

1. 按现有规则清洗并归一化输入。
2. 第一遍扫描通过每个状态预计算的最长 allow 长度标记白名单覆盖范围。
3. 第二遍扫描遍历 review 的直接输出和 suffix link，跳过被 allow 完整覆盖的命中并完整计算最高风险。
4. 执行有上限的 RE2 与组合规则。
5. 使用固定容量集合去重并保留确定性顺序的规则 ID；达到持久化上限时记录截断，但仍继续完成风险计算。

复杂度主要取决于输入长度和实际命中数，不随关键词总数线性增长。关键词长度上限为 500 字符，因此单个位置的 suffix 输出遍历也有明确上界；普通内容上限 2000 字符，管理员试跑上限 10000 字符。

### 6.2 索引文件

候选构建成功后通过流式接口写入版本化二进制索引文件，并保存到现有对象存储的 `moderation/rulesets/` 前缀。文件包含格式版本、规则集版本、各数组长度和校验和，不包含 Go 指针。

读取时先验证文件头、规则数、数组长度和配置上限，再流式解码到目标数组，禁止 `io.ReadAll` 和等长原始字节副本。启动时优先加载当前版本索引文件；文件缺失、格式升级或校验失败时从 MySQL 行流重建。`enforce` 模式下索引既无法加载也无法重建时拒绝启动。

### 6.3 单实例热切换

候选索引在当前快照之外构建。发布时：

1. 读取候选文件并完成校验。
2. 获取单进程规则发布互斥锁。
3. 在 MySQL 事务内确认 `base_ruleset_id`、应用停用关系并切换当前规则集。
4. 提交成功后原子替换内存快照；提交失败则丢弃候选。

分类请求始终无锁读取快照。提交与指针替换之间仍使用旧快照的极少数请求会保存旧规则集版本和旧规则 ID，审计语义仍准确。进程若在提交后、替换前退出，重启时加载数据库当前版本。系统不实现 Redis 发布通知、数据库版本轮询或多实例就绪状态。

### 6.4 候选缓存生命周期

manager 最多持有一个候选快照。构建完成后可短暂缓存供试跑和发布复用；发布、取消、失败或闲置 TTL 到期时立即清除引用。没有 handler、任务闭包或独立 timer 可以长期持有候选；TTL 由 worker 的单一周期检查完成。大型切片不进入 `sync.Pool`。

## 7. 容量与配置

新增配置：

```yaml
moderation:
  rules:
    max_pattern_chars: 500
    max_keyword_rules: 500000
    max_enabled_regex_rules: 200
    max_import_rows: 200000
    max_import_file_mb: 50
    max_rule_matches_per_content: 128
    max_index_memory_mb: 512
    max_build_peak_memory_mb: 1024
    index_build_timeout: 10m
    candidate_cache_ttl: 10m
    import_artifact_retention_days: 7
    ruleset_artifact_retention_days: 7
    import_history_retention_days: 30
```

所有配置支持 `BLOG_` 环境变量覆盖并在启动时校验为正数。`max_build_peak_memory_mb` 必须大于 `max_index_memory_mb`，正则默认值为 200 且配置硬上限为 500。

构建器按实际切片容量、节点、边、直接输出、数值规则元数据和当前/候选快照大小进行保守记账，并加入固定安全余量：

- 候选常驻估算超过 `max_index_memory_mb`：终止构建。
- 旧索引、候选索引和构建临时结构的峰值估算超过 `max_build_peak_memory_mb`：终止构建。
- 终止只标记候选失败，当前快照不变。

目标容量的规划值：10 万关键词常驻约 40–120 MB、构建峰值约 120–300 MB；50 万关键词常驻约 200–500 MB、构建峰值约 600 MB–1.2 GB。最终以真实词库基准结果为准。

## 8. 后台任务与导入流程

单进程 moderation worker 串行处理规则校验和索引构建，同一时间最多有一个正在构建或等待发布的候选规则集。其他导入任务排队，避免候选互相失效或同时占用大量空间。任务状态持久化，进程重启后将中断的校验或构建任务恢复到可重试状态。

导入流程：

1. 管理员上传 CSV 或 UTF-8 TXT；handler 流式限制请求体并通过对象存储流式接口保存原文件。
2. Worker 流式读取，验证 UTF-8、字段、行数、模式长度、类型、分类、风险和优先级。
3. 使用有上限的摘要集合检查文件内重复；数据库重复摘要按批查询，不执行逐行 SQL。
4. 错误报告边生成边流式上传；任意错误使校验状态进入 `invalid`，不创建候选规则行。
5. 无错误时创建候选规则集，并把候选规则按有界批次直接写入 `moderation_rule`；中途失败的未发布行由幂等清理删除。
6. 从当前已发布规则和候选规则的数据库行流构建索引，检查规则数和两个内存阈值，流式保存索引文件与统计。
7. 规则集进入 `ready`；管理员可查看统计、下载报告或使用候选版本试跑。
8. 管理员确认后用小事务发布规则集并原子替换快照。

导入是 add-only。CSV 内 `pattern` 必填，其他规则字段可由行值或上传表单默认值提供；行值优先。`name` 为空时保持为空。来源只能在任务级选择，不允许 CSV 每行覆盖。TXT 每个非空、非注释行是一条关键词，统一使用上传表单的分类、风险、效果和优先级。

## 9. 管理 API

全部接口挂载在 `/admin/moderation`，沿用管理员 JWT、统一响应和 normal 写限流。

### 9.1 规则

- `GET /rules`：基于规则 ID 游标分页，支持 ID 精确、模式精确或模式前缀搜索，以及分类、类型、风险、效果、状态和来源过滤；`limit` 最大 100。
- `POST /rules`：新增规则，带 `expected_ruleset_version`，自动创建、构建并发布候选。
- `PATCH /rules/:id`：创建替代规则，带 `expected_ruleset_version`，不覆盖旧内容。
- `POST /rules/batch-status`：最多 1000 个 ID，批量启用或停用并发布一个候选版本。
- `POST /rules/test`：最多 10000 字符，可选择当前版本或一个 `ready` 候选版本，返回命中规则 DTO 和最终风险。
- `GET /rules/export`：流式导出当前筛选结果的 UTF-8 BOM CSV，并防止电子表格公式注入。
- `GET /rules/status`：返回当前版本、候选任务、总规则数、索引统计和配置上限。
- `GET /rules/metadata`：返回分类、类型、风险、效果和来源目录，规则行 DTO 只携带稳定键或 ID。

列表返回 `next_cursor`，前端维护已访问游标栈以支持上一批/下一批，不返回总页数。模式搜索不接受默认 `%term%` 全包含扫描。新增、修改和批量状态操作返回发布任务。前端显示构建状态，当前规则集在任务成功前保持不变。`expected_ruleset_version` 过期返回 `409 MODERATION_RULESET_CONFLICT`。

### 9.2 导入

- `GET /rule-imports/template?format=csv|txt`：下载带字段说明的模板。
- `POST /rule-imports`：multipart 上传并创建任务。
- `GET /rule-imports`：分页查询任务历史。
- `GET /rule-imports/:id`：查询任务进度、统计和候选版本。
- `GET /rule-imports/:id/errors`：流式下载逐行错误报告。
- `POST /rule-imports/:id/publish`：发布 `ready` 候选，带 `expected_ruleset_version`。
- `DELETE /rule-imports/:id`：取消尚未发布的任务。

模板不得包含会被误发布的真实敏感词。CSV 模板使用以 `#` 开头的说明行、标准表头和一条明确停用的示例，导入器只允许在表头前跳过 `#` 说明行；TXT 模板仅包含以 `#` 开头的说明行。

## 10. 管理端设计

在 `../blog-frontend/apps/admin` 现有“内容审核”页面新增“规则管理”标签页，不新增独立导航入口。

### 10.1 页面结构

- 状态区：当前规则集版本、关键词/正则/组合数量、索引预计内存、最近发布时间和候选状态。
- 工具栏：新增规则、文本试跑、批量导入、下载模板、导出规则。
- 筛选：ID/模式精确或前缀搜索、分类、类型、风险、效果、启用状态和来源，并同步 URL 查询参数。
- 桌面端：游标分页表格和多选批量操作。
- 移动端：卡片列表，保留完整字段和行操作，不裁剪为不可操作的横向表格。
- 行操作：查看、修改、启用或停用。

新增和修改使用表单弹窗。提交后展示候选构建进度；成功后刷新状态和列表，冲突时提示刷新而不覆盖用户输入。

### 10.2 文本试跑

试跑弹窗允许选择当前版本或 `ready` 候选版本，输入测试文本后展示：最终风险、规则集版本、命中规则、分类、命中片段和是否被 allow 规则抑制。接口与 UI 只对管理员开放。

### 10.3 导入弹窗

分步流程：

1. 下载 CSV/TXT 模板或选择文件。
2. 设置 TXT 或 CSV 缺省字段的分类、风险、效果、优先级和来源。
3. 上传后显示解析、校验、去重和索引构建状态。
4. 展示总行数、有效数、重复数、错误数、节点数、预计常驻内存和峰值内存。
5. 错误任务可下载报告；`ready` 任务可执行候选版本试跑。
6. 管理员确认发布；发布成功后刷新规则列表和状态。

关闭弹窗不会取消任务。页面轮询活动任务；重新打开时从后端恢复状态。历史任务列表可重新查看统计和下载保留期内的报告。列表使用上一批/下一批，不展示虚假的总页数。

### 10.4 共享 API 包

在 `packages/api` 增加精确的规则、规则集、导入、匹配和分页 DTO，以及 multipart、文件下载和任务状态客户端方法。禁止 `any`；文件响应使用 `Blob`，业务错误码保持字符串类型供冲突和阈值分支判断。

## 11. 错误处理与安全边界

- 文件类型、MIME、扩展名、大小、行数和 UTF-8 必须同时校验；不接受 ZIP，避免解压炸弹。
- 对象存储增加显式流式读写接口；上传、导入、错误报告和索引文件路径不得退回 `[]byte` 整块缓冲。
- CSV 使用支持引号和换行的标准解析器，禁止自行按逗号切割。
- 错误报告包含行号、字段和错误原因；原始值只存在管理员下载文件，不写日志。
- 候选索引格式、长度和校验和不匹配时拒绝加载。
- 当前有效规则集不得为空；停用操作会导致空集时拒绝候选。
- 构建超时、内存超限、对象存储失败或 MySQL 失败均保留旧版本。
- 规则发布使用单进程互斥锁；同一时刻最多一个候选进入发布。
- 所有对象流、数据库 Rows 和临时文件在创建它们的函数内显式关闭；对象删除和候选清理必须幂等。
- 当前与 `ready` 候选的索引文件不得清理；失败、取消和 superseded 索引超过规则集产物保留期后删除，历史版本需要时从规则事实重建，避免每个版本永久保存数百 MB 文件。
- 管理端导出对以 `= + - @` 开头的单元格做安全转义。
- Handler 只绑定参数、读取管理员身份、调用 service 和映射统一响应。

## 12. 测试与验收

### 12.1 后端

- 分类器：关键词重叠、Unicode/繁简/全半角、allow 范围、最高风险、正则和组合规则，以及命中截断不改变风险。
- 索引：构建确定性、前缀嵌套不复制失败链输出、序列化/流式加载、边界校验、不可变快照、旧快照并发读取和原子替换。
- 容量：规则数上限、常驻内存上限、构建峰值上限和失败后旧版本继续工作。
- Repository：游标分页、摘要批查、规则集状态排除失败候选、版本区间、替代链、候选停用、任务恢复和发布事务回滚。
- Service：新增、修改、批量状态、重复检测、空规则集保护、版本冲突和候选试跑。
- Handler：管理员权限、分页边界、multipart 限制、模板/导出响应头及业务错误码。
- Import：CSV 引号/换行、TXT 注释、UTF-8、文件内重复、摘要批查、流式错误报告、候选中断清理和发布原子性。
- 资源：对象流和 Rows 在成功/失败路径均关闭，候选发布、取消、失败和 TTL 到期后 manager 不再持有快照。

Repository 使用 go-sqlmock，service 使用 gomock，handler 使用 httptest + testify。接口和 mock 变化后运行 moderation 相关测试、相关包 `go test -race` 及全量 `go test ./...`，再执行 `make swag` 并确认 Swagger 只引用 DTO。

### 12.2 前端

- `packages/api`：路径、查询参数、请求体、multipart、Blob 下载和业务错误保留。
- Hook：游标栈、筛选重置游标、任务轮询、关闭后恢复、冲突刷新和发布后刷新。
- 组件：规则表单、批量启停、模板下载、导入各状态、错误报告和候选试跑。
- 页面：新增标签页、loading/error/empty/success、桌面与移动布局。

按前端规范为 Hook、组件和页面补齐 Vitest 测试，运行相关包测试、类型检查和 admin 构建。

### 12.3 性能基准

使用确定性生成器分别创建 10 万和 50 万条关键词，记录：

- 归一化后有效规则数及重复率。
- 节点、边和输出数量。
- 构建耗时、索引文件大小、常驻内存估算和构建峰值估算。
- 800、2000 和 10000 字符输入的无命中、少量命中和大量命中耗时。
- 连续构建和发布 20 次后的可达快照数、堆增长趋势和每次分配量。

性能测试输出报告，不用脆弱的绝对耗时或“发布后 RSS 立即下降”作为普通单元测试断言；Go 运行时保留堆不等于泄漏。内存阈值、规则上限、候选引用清理和前缀嵌套输出规模必须作为确定性测试断言。
