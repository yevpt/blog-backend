# 图片上传链路收尾加固设计

## 目标

修复图片上传重构后遗留的三个问题：multipart 代理复用已消费请求流、同一用户跨碎语复用图片导致坏链，以及部分单文件接口未限制 multipart 文件 part 总数。同时修正头像尺寸规则升级后失效的测试夹具。

## 前端 multipart 认证

`proxyPostForm` 必须保持流式转发，不缓存或复制完整请求体。代理在发送请求体前使用现有 `isAccessTokenValid` 判断 access token：无效或过期时先使用 refresh token 换发；换发成功后仅发送一次 multipart 请求。

普通 JSON、GET 等可重放请求继续保留后端 401 后刷新并重试的行为。multipart 请求关闭发送后的透明重试：若一个结构有效的 token 被后端撤销，代理透传后端 401，不把一次性流重试失败伪装成 502。

回归测试覆盖：

- 过期 access token 与有效 refresh token 会在上传前续期，multipart 只发送一次。
- 后端对 multipart 返回 401 时不进行第二次上传，并透传 401。
- 既有流式透传、体积限制和幂等键行为不变。

## 碎语图片归属

普通碎语保存时，已有图片 key 必须属于当前碎语目录 `moments/{userID}/{momentID}/`，仅属于当前用户不再足够。无序和显式排序两条处理路径使用同一校验。

审核链路遵循相同边界：

- 编辑碎语时，只允许复用 `moments/{authorID}/{req.ID}/` 下的已持久化图片。
- 新建碎语时不允许通过 `image_urls` 借用任意历史碎语图片。
- 本次请求携带的新文件仍上传到现有审核暂存目录，不改变审核资源生命周期。

这样无需引入共享引用计数，并从入口消除跨碎语共享对象造成的删除坏链。

回归测试覆盖同一碎语复用成功、同用户跨碎语复用失败、跨用户复用失败，以及审核新建和编辑的对应边界。

## multipart 文件数量

友链 Logo、音乐上传、审核规则导入均为单文件接口。在请求体总大小保护之后、`FormFile` 触发 multipart 解析之后，统一调用 `multipartlimit.RejectExcessFileParts(c, 1)`。只要所有字段合计超过一个文件 part，就返回现有业务错误“上传文件过多”，不进入 service 或对象存储。

每个 handler 增加两个文件 part 的回归测试。既有单文件大小、真实内容校验、权限和清理流程不变。

## 测试夹具

头像和友链 Logo 的合规尺寸已从 120px 提升到 240px。头像归一化测试中的“超限图片”由 200×200 调整为大于 240×240，保持测试语义，不改变生产规则。

## 验证

- 前端运行 `pnpm test:run` 与 `pnpm check-types`。
- 后端先运行受影响 package 测试，再运行 `go test ./...`。
- HTTP 注解和响应结构未变化；仍运行 `make swag`，确认生成文档无意外漂移。
- 两个仓库最终保持无非预期改动。
